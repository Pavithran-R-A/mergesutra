# MergeSutra v0.1.0 — release candidate notes

MergeSutra v0.1.0 is the first consumer release candidate of the BharatCode-powered
CLI for turning a GitHub issue into a structured, evidence-backed pull-request
candidate.

## What ships

- GitHub issue intake and repository identity pinning.
- Repository policy discovery and an explicit Acceptance Contract.
- BharatCode planning, bounded implementation and independent review stages.
- Isolated Git worktrees, confined writes, command-risk classification and secret
  redaction.
- Human-consented verification gates with exit-code receipts.
- Evidence packs mapping acceptance criteria to measured verification.
- Digest-approved repair cycles that re-run verification after changing bytes.
- A locally approved pull-request candidate, plus read-only status and one-stage
  resume/recovery.
- GitHub-hosted CI on Ubuntu and Windows with Node 22 and 24.
- Hosted path-shape qualification for spaces, temp roots, Windows drive/separator aliases, HOME/USERPROFILE, and real Git/gh discovery.
- Runtime dependency audit, package-boundary verification and fresh packed-artifact
  installation.
- Release automation prepared for npm Trusted Publishing through GitHub OIDC.

## What does not ship

- `mergesutra run` remains planned; there is no unattended all-stages pipeline.
- The production CLI does not commit, push or open a GitHub pull request. `pr`
  prepares the page and records the human approval locally.
- A worktree is not an OS sandbox.
- macOS is not qualified by hosted CI.
- The controlled real-BharatCode Stage-14 run and approximately ten-task benchmark
  are not yet evidence this repository can claim, because no real provider
  credential is available to the current release environment.

## Release quality boundary

The release candidate is accepted only after the four hosted CI matrix jobs pass
all deterministic gates. Runtime dependencies are audited separately from the
known dev-toolchain advisories so a development-only advisory cannot be confused
with code that ships to consumers.

The first npm publication requires one interactive npm-account/2FA bootstrap.
After the package exists, subsequent releases are designed to use the repository's
OIDC trusted-publishing workflow without a long-lived npm token.
